# 长文档索引并发与续跑修复

日期：2026-11-10，Asia/Shanghai。

## 问题与修复范围

原实现逐批等待 Embedding、逐段等待图谱抽取。现场 PDF 有 318 个父分段、3,302 个子分段，向量阶段预计耗时约 37 分钟，后续串行图谱阶段可能使单次 Celery 执行超过 3,600 秒。向量状态已有恢复基础，但图谱抽取没有可复用的完成检查点。

此次保留现有索引任务、版本发布和持久化模型，补齐以下行为：

- Embedding 与图谱模型请求使用有界并发。每次仅保留配置数量的请求及结果，结果与原始分段绑定；数据库 session、向量确认和图数据写入由单个消费流程协调。
- 图谱结果和完成指纹在同一个 Neo4j 事务内提交。指纹包括分段正文、模型、抽取版本和 schema 配置；成功的空抽取也记录。续跑跳过完成结果，配置变化后重新抽取。
- Worker 默认使用 900 秒时间片。完成检查点后可以归还执行机会、重新入队；正常续跑不消耗失败尝试次数。原有 Beat 补投器继续负责派发 pending 文档任务。
- 首次解析、分段及警告作为完整检查点保存。准备阶段超过时间片时，先安全保存该检查点；下一次执行直接加载暂存分段，避免重复解析或无限重来。
- 每个时间片至少允许完成一个有效处理单元，避免单次正常模型请求比时间片长时反复取消、没有进展。未完成任何新检查点即达到实际软时限的执行，仍计为有上限的失败重试。
- 经济索引关键词按批保存；高质量索引关键词同样按批提交，续跑跳过已完成结果。取消或异常不会使已确认的结果重新计算。
- 慢外部请求等待期间检查取消并更新租约；同步解析线程退出之前保留其资源和租约。取消状态直接查询数据库标量状态，避免长生命周期 session 缓存隐藏外部取消。
- 续跑不回退文档的显示进度。失败的全量索引重试时将目标版本恢复为 building，使成功重试能够正常激活。
- 图谱模型返回截断或结构无效的 JSON 时，仅追加一次带有界 JSON Schema 的格式恢复请求；不接受部分 JSON，也不把失败记录为完成。普通请求继续使用 JSON 模式。抽取提示明确实体去重，恢复请求最多 6 个实体、8 条关系及 2,048 输出 token，恢复时属性为空对象；请求采用 `frequency_penalty=0.5` 抑制重复输出。

## 配置

| 配置 | 默认值 | 作用 |
|---|---:|---|
| `EMBEDDING__MAX_CONCURRENCY` | 4 | 单文档的并发 Embedding 请求上限 |
| `GRAPH__MAX_CONCURRENCY` | 4 | 单文档的并发图谱模型请求上限 |
| `INDEXING__HEARTBEAT_INTERVAL_SECONDS` | 10 | 慢请求期间的取消与租约检查间隔 |
| `INDEXING__TASK_SLICE_SECONDS` | 900 | 检查点之间的协作时间片 |
| `INDEXING__TASK_SOFT_TIME_LIMIT_SECONDS` | 3500 | Celery 单次执行软时限 |
| `INDEXING__TASK_TIME_LIMIT_SECONDS` | 3600 | Celery 单次执行硬时限 |

时间片加心跳间隔必须小于软时限，软时限必须小于硬时限。初次准备仍受实际软、硬时限保护，不能将无法完成的准备阶段无限当作正常续跑。

无需新增数据库迁移。分段正文、向量状态和解析警告复用现有 PostgreSQL 字段，图谱检查点使用 Neo4j 节点属性。

## 本地模型容量与实际测量

本地 TEI 原配置 `--max-concurrent-requests=4`，实际按输入容量限制：4 段请求成功，8 段和 16 段请求立即返回 429。服务返回的 `max_client_batch_size=32` 不代表当前并发容量也允许 32 个输入。

本地 Compose 配置现为 64 个输入并发、32 个批处理请求，应用模型批量为 16。保持 BGE Large Chinese v1.5、1,024 维、每段不超过 500 字符，不更换模型或缩短原文。

真实原 PDF 的同一组 32 个分段测量如下：

| 服务容量 | 应用批量 | 应用并发 | 向量数 | 耗时（秒） |
|---:|---:|---:|---:|---:|
| 4 | 4 | 1 | 32 | 20.048 |
| 64 | 4 | 1 | 32 | 20.550 |
| 64 | 16 | 1 | 32 | 20.648 |
| 64 | 16 | 4 | 32 | 20.485 |
| 64 | 32 | 2 | 32 | 20.682 |

该 CPU Embedding 服务已经受模型计算吞吐限制，本轮未测出显著向量计算提速。扩大容量解决 429 并允许并发，但不能据此宣称当前 CPU 向量推理快了数倍。

本地原生 Ollama `graph-qwen2.5:1.5b` 的同一组 4 个图谱片段：串行 1.658 秒，并发 4 时 0.540 秒。该结果仅是小样本模型请求测量，不包含全量图写入，也不能直接当作整个文档的提速倍数。

## 自动化与真实环境验收

自动化覆盖并发上限、结果乱序、取消后请求清理、慢请求心跳、同步线程取消、图谱检查点与配置失效、时间片不消耗失败次数、软超时、准备阶段跨时间片、关键词跨时间片、外部取消可见性、进度保留和失败索引重新激活。

真实长文档用例：`tests/integration/test_long_document_indexing.py`。使用同一份 11,084,397 字节 PDF，目标为 318 个父分段和 3,302 个子分段。用例使用独立 PostgreSQL schema，实际调用 MinIO、BGE、Milvus、Ollama 和 Neo4j；主动在图谱阶段中断一次，随后检查续跑不再次向量化，核对分段、向量和图谱检查点数量并检索证据。

真实 RabbitMQ/Worker 用例：`tests/integration/test_celery_time_slice.py`。使用独立数据库与队列，将时间片设置为 1 秒；首次续跑之前删除自己的测试原文件，验证后续实际 Celery 投递可直接从数据库分段检查点继续。

两种验收默认均清理自己创建的业务数据和外部存储对象，不修改现有知识库。排查长文档失败时，可显式设置 `PERF_KEEP_ON_FAILURE=1` 保留该次测试资源，再设置 `PERF_RESUME=1` 从报告指向的独立 schema 继续；成功后仍自动清理。恢复路径核对 schema 名称、任务与目标索引、知识库及文档关系后，才允许清理相应外部对象。

运行命令：

```bash
.venv/bin/python -m pytest -q
RUN_CELERY_RESUME=1 .venv/bin/python -m pytest tests/integration/test_celery_time_slice.py -q -s
RUN_LONG_INDEXING=1 PERF_SOURCE_PDF=/absolute/path/to/source.pdf \
  .venv/bin/python -m pytest tests/integration/test_long_document_indexing.py -q -s
```

真实用例需要宿主机可访问的服务地址与正确凭据。可用 `PERF_EXPECTED_CHILDREN` 调整其他样本的预期子分段数；本次原 PDF 使用默认值 3,302。

当前自动化验证：后端 `795 passed, 13 skipped`；前端 Playwright `18 passed`；前端构建通过。13 个默认跳过项包含显式启用的外部服务用例，不代表这些服务均未验证。

已显式运行的真实服务验证：MinIO/Milvus 集成 `4 passed`；独立 RabbitMQ/Celery 续跑 `1 passed`。Celery 用例完成 4,500 个分段，经过 3 次实际投递，业务完成耗时 14.413 秒，最终 `attempt=1`，首次切片后原文件已删除。该用例的计时不含 Worker 退出及测试清理时间。

更新镜像并重启本地 API/Worker 后，真实 HTTP 端到端用例 `tests/integration/test_console_flow.py` 为 `3 passed`，覆盖上传下载、实际 Worker 索引、检索与 SSE、文档状态管理、分段修订、导入导出及删除。

首次原 PDF 验收已完成全部 3,302 个向量，随后在图谱 165 段处失败：本地 1.5B 模型重复生成同名实体，达到 1,024 token 输出上限后留下截断 JSON，三次任务尝试均得到相同结果；续跑未重复向量化。原始失败报告保留为 `full-pipeline-first-failure.json`。新增有界格式恢复后，三个已复现的失败片段均通过真实模型调用得到有效结果。后续又在原文位置 451 复现 4,096 token 恢复响应仍被截断，因此进一步收紧恢复结构并抑制重复输出。原文位置 179、180、184、451 在最终请求逻辑下均得到有效结果，分别耗时 0.872、0.560、1.045、1.383 秒；这仅是问题片段测量。验收进程已替换并从同一独立 schema 恢复全部真实向量，图谱按更新后的指纹重新处理。最终原 PDF 验收已通过，结果如下。

最后一次验收进程耗时 3,259.91 秒（约 54 分 20 秒），包含最终抽取版本的全量图谱处理、激活、检索和清理；向量复用之前实测生成的 3,302 条结果。报告累计处理计时为 7,327.004 秒（约 122 分 7 秒），包含早期向量请求失败重试、旧抽取版本的排查及处理，且恢复计时未计入进程替换期间的停顿。该累计值不作为最终代码一次全新端到端运行的性能基准。

向量阶段累计请求 3,494 个输入，包含请求失败和切片取消后的未确认在途输入；最终仅有 3,302 个向量。最终恢复阶段未重复任何已确认向量。图谱版本变化会重新抽取，普通时间片恢复则按当前配置指纹跳过完成项。

验收结束后另行确认：独立 PostgreSQL schema 已删除、该测试的 Milvus collection 不存在、Neo4j 相关节点为 0、MinIO 测试原文件对象为 0。完整报告为 `full-pipeline.json`，清理核对为 `cleanup-verification.json`。
