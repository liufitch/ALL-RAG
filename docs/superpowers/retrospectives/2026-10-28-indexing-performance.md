## 2. 已确认的主要瓶颈：本地模型小批量串行向量化

运行时使用本地 TEI 服务中的 `bge-large-zh-v1.5`，向量维度 1,024。
模型配置的 `batch_size=4`、`max_input_characters=500`；索引引擎逐批等待
Embedding、Milvus 写入和数据库完成状态更新，然后执行下一批。

现场日志统计：

- 同一任务已产生 150 次成功的向量请求，平均服务端请求耗时约 2.695 秒。
- 请求持续返回 HTTP 200；子分段完成数从 564 增长到 584、600，心跳持续更新。
- 容器资源采样中，Embedding CPU 约 338%，Worker CPU 约 1.17%，PostgreSQL
  CPU 约 0.40%，Milvus CPU 约 2.81%。此采样支持主要时间花在模型推理的判断。
- Embedding 容器的 cgroup 计数中没有 CPU 配额节流记录，也没有 OOM 记录；
  不能仅因存在 2 GiB 内存限制就断言发生了内存不足。
- Embedding 镜像为 `arm64`，宿主机为 `arm64`；本次证据不支持将该服务的
  缓慢归因于 x86 架构仿真。API/Worker 使用 `amd64` 镜像，但不是当前主要 CPU 消耗方。

按采样吞吐作线性估算：

```text
ceil(3,302 / 4) = 826 批
826 × 2.695 秒 ≈ 37 分钟（向量请求累计时间）
采样时剩余 2,702 段，剩余向量请求时间约 30 分钟
```

这是估算，不是完整索引实测耗时，也不包含后续关键词处理、图谱抽取和最终激活。
CPU 负载、输入长度和模型服务速度变化都会影响结果。

## 3. 后续耗时与超时风险：逐段串行图谱抽取

Worker 运行时已启用 `GRAPH__ENABLED=true`，图谱抽取模型为本机 Ollama 的
`graph-qwen2.5:1.5b`。向量化及关键词处理之后，索引引擎仍会等待
`GraphIndexer.index` 完成，才能报告验证完成。

`GraphIndexer.index` 对每个可索引子分段逐一调用抽取模型，再写入 Neo4j，
没有分段间并发。这份文档按当前实现还需要 3,302 次图谱抽取请求。
调查时任务尚未进入图谱阶段，未测得本任务的单段抽取时间，不能将其计入
已经发生的向量化耗时，也不能给出确定的最终完成时间。

已确认的代码风险：

- Celery 软超时为 3,500 秒，硬超时为 3,600 秒；向量化预计已需约 37 分钟，
  加上图谱抽取后存在超过单任务时限的风险，调查时尚未发生超时。
- 图谱循环未逐段报告进度、续租心跳或检查取消；文档任务租约为 300 秒。
  长时间抽取与租约恢复、取消流程的交互需要专项验证，尚未确认本次已发生重复执行。

## 4. 进度与任务汇总问题

### 4.1 显示 74% 时，实际只完成约 18% 的子分段向量

索引引擎在第一批向量请求后将阶段进度设为 70%，后续批次映射到 70%～95%。
因此 74% 是固定阶段权重的结果，不能解释为总耗时或向量处理量已完成 74%。
图谱抽取也没有单独的阶段进度，后续可能长时间停留在 95%。

### 4.2 任务汇总与文档任务状态不一致

调查时 `indexing_job_documents` 已为 `running` 且完成数持续增长，
但对应 `indexing_jobs` 仍为 `pending`、进度 0。代码中 `heartbeat` 更新
文档任务，`refresh_job_summary` 在任务运行器结束的 `finally` 中调用。
需要核对 API 和前端采用哪个层级的状态，并补齐运行中的汇总刷新。
当前只确认数据库快照存在差异，未验证用户界面是否因此显示待处理。
