# 2026-11-10 索引与知识库生命周期修复记录

日期：2026-11-10，Asia/Shanghai。

## 范围与结论

本轮修复用户确认的三个问题：追加文档建立索引后原有文档无法检索；删除知识库后部分接口仍能访问内容；长文档 Embedding、图谱抽取串行执行且可能超过单次 Worker 的 3,600 秒硬时限。真实验收还发现本地图谱模型重复生成实体并返回截断 JSON，本轮一并处理。

修复已应用到本地 API/Worker 镜像。无需新增数据库迁移。长文档的配置、采样、失败排查和完整验收详见[性能与续跑验收记录](../../2026-11-10-indexing-performance.md)。

## 1. 追加文档后原有内容无法检索

### 问题与影响

已有可用索引的知识库追加文件并确认索引后，原文档的证据不再被检索。用户仅选择新文档，却可能导致整库有效索引切换。

### 原因

- 配置确认流程始终创建 `initial_index` 任务和新的 `building` 索引版本，没有区分首次建库与向已有索引追加文档。
- 新版本只包含本次选中文档；全量发布时退役旧索引，原文档虽然仍有分段和文件，却不再属于可检索的有效版本。
- 前端配置面板使用全局默认配置，未加载知识库已保存的索引方式、Embedding 模型和分段规则，追加时可能无意改变参数。
- Worker 汇总状态可能先于索引发布变为 `completed`。仅判断任务运行状态不能识别“处理完成但尚未发布”的窗口。
- 增量发布若不按当前任务筛选暂存分段，可能混入失败任务的残留数据；重复发布也需要保持幂等。

### 解决方案

1. 配置确认时锁定未删除的知识库，查询当前有效索引，并阻止与运行中或待发布任务重叠的确认。
2. 首次索引仍创建新版本；已有有效索引时创建 `reindex_documents` 任务，复用当前目标索引，仅处理本次选中文档。
3. 校验索引方式、Embedding 模型及分段规则与有效索引一致。不一致返回 `409`，配置变更通过全库重建流程完成。
4. 前端同时加载索引选项与知识库设置，以已保存配置初始化追加面板。
5. 增量发布只接收当前 `indexing_job_id` 的暂存结果，核对每个选中文档均有完整、可发布的分段；只替换选中文档的旧分段，保留其他文档。
6. 已发布任务重复收到最终化请求时保留成功状态，避免将已完成任务误判为失败。

### 验证与边界

- 回归覆盖经济索引与高质量索引：追加第二个文档后，原文档和新文档的证据均可检索，有效索引仍为同一个版本。
- 覆盖参数冲突、初次索引待发布、增量任务待发布、失败暂存隔离及重复发布。
- 前端浏览器测试确认追加面板沿用已保存配置。
- 本次不会自动恢复此前已被错误退役的旧分段。受影响的历史知识库应先确认原文件可用，再执行全库重建。

主要实现：`ProcessRuleService`、`ProcessRuleRepository`、`IndexingRepository.finalize_indexing_job`、`IndexingPanel.jsx`。

## 2. 删除知识库后仍能访问内容或执行操作

### 问题与影响

知识库软删除后，直接使用其 ID 仍可能检索旧证据、下载原文件、查看索引任务或进入分段修订。历史上仅标记知识库删除、尚未清理子记录的数据也存在同样问题。

### 原因

- 部分入口只检查文档、任务或索引自身的状态，没有同时检查父知识库的 `deleted_at`。
- 检索服务选择有效索引时未关联知识库删除状态，导致存留的有效索引仍可参与召回。
- 分段修订在检查父知识库前先处理版本冲突，删除后的请求可能返回 `409` 等内部状态信息。
- 检索依赖可能先连接模型或存储服务，再判断知识库是否存在，影响删除后接口的稳定行为。

### 解决方案

1. 添加 `require_active_dataset` 依赖，索引任务入口和检索服务初始化前校验知识库，删除后返回 `404`。
2. 文档仓储查询关联未删除知识库；检索索引查询也关联知识库状态，覆盖绕过 HTTP 的直接服务调用。
3. 索引配置服务检查并锁定父知识库，将不存在/已删除场景映射为 `404`；一体化上传索引接口保持失败上传补偿。
4. 分段修订先校验并锁定父知识库，再检查文档及修订版本；知识库删除同样取得行锁，协调删除与配置/修订。

### 验证与边界

- 参数化 API 回归验证删除后的检索、SSE、文档列表、下载、分段、文档状态操作、任务列表/详情/重试/取消、配置、设置、重建与导出等入口返回 `404`。
- 覆盖历史仅软删除父知识库的记录；直接文档查询返回空，直接检索服务不返回证据。
- 验证删除请求在连接检索提供方前被拒绝，分段修订在旧版本冲突或没有有效索引时仍优先返回 `404`。
- 本轮修复保证读取与业务操作不可访问；底层对象和向量的物理清理由现有清理任务负责。

主要实现：`api/dependencies.py`、`indexing_jobs_api.py`、`retrieval_api.py`、`DocumentRepository`、`RetrievalService`、`DocumentRevisionService`。

## 3. 长文档串行处理、超时与恢复问题

### 原因

- Embedding 按批串行等待，图谱按分段串行等待；3,302 个子分段的总计算时间可能超过一次 Worker 执行时限。
- 图谱没有与成功写入绑定的完成检查点，失败后会重复调用模型。
- 本地 TEI 原并发容量为 4，批量扩大到 8 或 16 个输入会立即返回 `429`；容量与客户端批量上限不能混为一谈。
- 准备阶段、关键词批次和同步解析线程若缺少持久化或等待期间的心跳，会影响续跑、取消和租约。
- 长生命周期 SQLAlchemy session 可能缓存旧状态，隐藏外部取消；失败重建的目标版本若一直为 `failed`，成功重试后也无法激活。

### 解决方案

- 模型请求采用有界并发，默认 Embedding 与图谱各 4；结果始终绑定原始分段。数据库 session、向量确认和图写入由单个消费流程协调。
- 默认 900 秒协作时间片，完成检查点后归还并等待现有 Beat 补投；正常切片不消耗失败次数。保留 3,500/3,600 秒软硬时限，每次执行允许完成至少一个新处理单元；实际软超时且无新检查点的情况仍有界重试。
- 保存完整解析分段和警告检查点；向量、关键词按批确认，图谱结果与指纹在同一 Neo4j 事务提交。成功的空抽取同样记为完成，配置变化使旧指纹失效。
- 慢请求等待期间每 10 秒检查取消并续租；同步线程退出前保留资源与租约。通过数据库标量查询读取最新取消、删除和 Worker 所有权。
- 续跑保留显示进度，失败的全量索引重试时恢复目标版本为 `building`。
- 本地 TEI 调整为 64 个输入并发、32 个批处理请求，应用批量为 16，解决服务容量不匹配。

### 验证与限制

- 单元与集成测试覆盖并发上限、乱序结果、取消清理、慢请求心跳、同步线程退出、图谱配置失效、时间片及软超时、准备/关键词续跑、外部取消和重试激活。
- 真实 RabbitMQ/Celery 用例完成 4,500 个分段，经过 3 次投递，最终 `attempt=1`；首次切片后删除测试原文件，仍能从数据库继续。
- 原 PDF 完整验收通过：318 个父分段、3,302 个子分段、3,302 个向量及 3,302 个图谱检查点，索引为 `active`，实际检索返回 5 条证据。
- 最终图谱版本经过 4 个时间片完成，新增向量请求均为 0。最终恢复进程耗时约 54 分 20 秒，复用先前实测向量；不是从零建立整份文档索引的耗时。
- 本机 CPU Embedding 仍受模型计算吞吐限制，相同 32 段采样约 20 秒，未测出显著推理加速。并发与续跑不代表整份文档必定在 60 分钟内完成。

## 4. 图谱模型重复输出与截断 JSON

### 原因

真实验收在图谱 165 段处发现小模型反复生成同名实体，达到 1,024 token 上限后返回不完整 JSON；三次任务尝试得到相同结果。初版格式恢复在另一表格片段中仍生成过长名称和属性，达到 4,096 token 上限。单纯重复同一请求或增加输出预算不能解决该问题。

### 解决方案

- 提示实体去重并采用标准 `frequency_penalty=0.5` 抑制重复。
- 普通调用保留 JSON 模式；遇到截断或结构无效结果时，只追加一次紧凑 JSON Schema 恢复请求。
- 恢复请求限制为最多 6 个实体、8 条关系和 2,048 输出 token，属性使用空对象，明确禁止把整行表格或长段落当作实体名称。
- 只返回完整且通过解析的事实，继续过滤原文中不存在的实体；恢复失败显式报错，不接受部分 JSON 或伪造完成检查点。
- 将抽取版本纳入指纹，最终版本为 3，配置更新后重新抽取图谱，复用有效向量。

### 验证与边界

- 回归覆盖无效 JSON、无效结构、`finish_reason=length`、一次恢复上限及不返回部分事实。
- 原文位置 179、180、184、451 在最终逻辑下均通过真实模型调用，随后全量图谱验收通过。
- HTTP 失败仍显式报错，取消可传播；仅支持普通 JSON 模式的提供方可正常完成首个请求，但无法完成 JSON Schema 恢复。
- 紧凑恢复优先保留少量明确实体和关系，恢复结果不包含实体属性；普通成功响应仍保留其有效属性。
