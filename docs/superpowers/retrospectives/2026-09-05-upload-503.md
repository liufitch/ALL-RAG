# 2026-09-05 上传 503 排查与修复

## 现象

用户报告 `POST /api/knowledge_base/7ebc8e3090414ca0984c45b6041aba30/documents/upload` 返回 503。工作区中的前后端上传路径已由用户调整为 `/documents/upload`，本轮保留该正式入口。

## 已验证的原因

1. 同一知识库的文档 GET 返回 200，排除该读取环节的数据库故障；MinIO `localhost:9000/minio/health/live` 也返回 200。
2. 应用生效配置的对象存储 access key 和 secret key 均为空。使用相同配置执行只读 bucket 检查，SDK 返回 `S3Error(code=AccessDenied)`，说明请求匿名且被拒绝。上传 API 将该异常统一转成 503，所以只有访问日志无法看到具体原因。
3. 经许可从本机现有 MinIO 容器读取认证配置（只在内存中处理，不输出值），认证检查通过，确认上传 bucket 尚未创建。当前容器使用旧式 `MINIO_ACCESS_KEY/MINIO_SECRET_KEY` 名称，而非 compose 文件中的新式 ROOT 名称；没有改动运行中的容器配置。
4. 将凭据保存到根目录 `.env` 后，配置检查仍为空。进一步追踪确认 `BASE_DIR` 是 `rag_modules/config`，旧代码只读该目录的 `.env`，与项目根目录 `.env.example` 的使用方式不一致。

## 复盘结论

- 服务存活不代表认证可用，应分别检查网络、认证、bucket 和业务提交。
- dotenv 路径应明确相对于项目还是模块；根目录示例必须与程序读取位置一致。
- 503 对客户端保持简洁，服务端需保留不含敏感信息的错误类别，避免只剩一行访问日志。
- 修改凭据文件后需要后端重载；该项目配置和 storage adapter 均为进程级缓存。
