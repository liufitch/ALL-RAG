# Phase 4 Task 5 Report — Single-Document Indexing Engine

Date: 2026-09-04

## Design and pre-implementation self-check

- The engine accepts one immutable command containing the existing `SegmentStagingCommand`, source object identity (`object_key`, `filename`, `extension`), the immutable segmentation config, embedding model/batch settings, and the optional existing-index vector target snapshot. Economy commands require general segmentation and forbid model/target data. High-quality commands require a model; existing targets require both collection name and expected dimension, while building targets require neither. All command/target validation precedes object-storage access.
- The observable stage sequence is exactly `download -> parse -> split -> stage -> embed-or-keywords -> vector-upsert -> validate`. Cancellation is checked before each stage and each engine-visible batch. Progress uses fixed stage bands and batch fractions, so it is deterministic and monotonic and reports only stage, integer progress, and aggregate segment counts.
- Object storage and Embedding remain asynchronous. Parsing, segmentation, keyword extraction, and synchronous vector-provider calls are offloaded with `asyncio.to_thread`; the storage stream remains inside its asynchronous context for the whole parser call and exits deterministically on success or failure.
- Staging delegates identity and PostgreSQL row creation to `SegmentRepository.stage(SegmentStagingCommand, segments)`. High-quality general rows and parent-child child rows are indexable; parents stay PostgreSQL-only with `embedding_status=not_required`. Economy updates bounded keywords through a public, commit-free repository method and never reaches Embedding, target resolution, or Milvus.
- For an existing high-quality target, the command target is used directly and the resolver is forbidden. For a building target, the first non-empty embedding batch discovers the dimension, resolution occurs exactly once, the returned target is validated, and the dimension is locked before any vector write. Vector payloads exist only as `VectorEntity` values sent to the vector provider; the engine and staging repository never accept or write a PostgreSQL vector.
- Each successful vector upsert must return exactly its batch size. Only then does the repository flush that batch's `embedding_status=completed`. A later failure therefore preserves only earlier successful-batch status changes. Task 5 does not activate rows or soft-delete prior versions.
- Single-document `vector_count` is the exact sum of successful upsert return values, validated against this document's indexable row count. The adapter's `count(collection)` is deliberately not called because it is collection-wide and is invalid for parallel/appended documents; whole-collection validation belongs to Phase 5 finalization. The cost is that this engine proves acknowledged per-document writes, not independent collection cardinality.
- Parser and segmentation warnings are reduced to a bounded immutable list of stage/code pairs. Error types expose stable code, retryability, and fixed safe messages; source text, vectors, object keys, credentials, and backend bodies never enter progress, warning text, or engine-generated errors.

## Residual risks

- This unit-scoped task uses deterministic fakes for object storage, Embedding, target resolution, and Milvus. The existing adapter tests cover their public boundaries, but a real PostgreSQL/MinIO/Embedding/Milvus end-to-end run remains later integration/finalization scope.
- Acknowledged per-batch upsert counts prove this document's submitted writes, not independent collection cardinality. This is the deliberate single-document ruling; Phase 5 must coordinate whole-index validation, activation/version switching, and failure compensation.
- Repository mutation methods flush but do not commit. Phase 5 owns transaction disposition after partial external success and must preserve/retry the intended earlier-batch state consistently with its job policy.
- Cancellation waits for non-cancellable synchronous parser/segmenter/vector work to exit before releasing owned resources. This favors lifecycle correctness; hard deadlines/worker-process termination remain orchestration concerns.
